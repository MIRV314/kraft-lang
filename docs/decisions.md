# Решения по языку и реализации

Этот файл — источник истины для компилятора. README объясняет язык
программисту; здесь — что именно считается правильным. Если README и этот
файл расходятся, прав этот файл (и README надо поправить).

Пути в старых записях исторические: с v0.2.0 служебные файлы (`kraft`,
`src/`, `tests/`, `xkraft.kraft`, `Makefile`) лежат в `dev/`, а готовый
бинарник — в корне и в `dist/`. Установленные `xkraft` и `kraft` — один
и тот же x-бинарник.

Терминология: `kraft` (также `xkraft` и псевдоним `kraft`) — основной
бинарник текущей версии. `dev/kraft` всегда называется «замороженный `kraft`
v0.1»: он служит только для сборки `xkraft.kraft` и не меняется. Где в старых
записях сказано «kraft v0.1», имеется в виду именно `dev/kraft`.

## Язык

**D0. Имя.** Ранний вариант `craft`; заменой первой буквы получено `Kraft`.
Название не описательное и не отражает назначение языка.

**D1. Статическая типизация.** Тип переменной задаётся объявлением и не
меняется. `flint` — один числовой тип (внутри double): целые и дробные не
различаются. Неявных приведений между числами и коллекциями нет; правило
`str → flint` описано в D99.

**D2. `NONE` — обычное значение.** Его можно писать в коде и присваивать
переменной любого типа. Это не «сломанный тип», а пустое значение.

**D3. Операции с `NONE` падают в рантайме.** `NONE + 1` →
`TYPE_MISMATCH_ERROR`. Переприсвоил число — переменная снова нормальная.
Исключения: `==`, `!=`, `is NONE`, `show`, присваивание, `return:`.

**D4. Полная статика, кроме чтения из коллекции без параметра типа.**
`list`/`dict` без параметра могут хранить разные типы; чтение из них
проверяется в рантайме. `list[flint]`/`dict[str|flint]` закрывают дырку.
Никакого типа `any` в языке нет — только внутренняя пометка компилятора.

## Функции и возврат

**D5. `-> тип` опционален.**
- есть аннотация — это контракт, каждый `return` проверяется;
- нет аннотации — тип выводится: все `return expr` должны давать один тип;
- `return:` (пустой) совместим с любым типом, но помечает «может быть NONE»;
- нет `return` вообще — функция типа `NONE`.

**D6. Разные типы в `return` без аннотации — ошибка компиляции**, а не
«неизвестный тип».

**D7. Рекурсия без `->` — ошибка:** тип из себя самого не выводится.

**D8. `-> NONE` не пишется.** Пустой возврат — это отсутствие `->`.

**D9. Аннотации возврата:** `-> flint`, `-> str`, `-> bool`, `-> list`,
`-> list[flint]`, `-> dict`, `-> dict[str|flint]`.

**D10. `--types` — не в v0.1.** Отладочный вывод сигнатур отложен.

## Область видимости

**D11. Область — функция.** Объявление видно с точки объявления до конца
функции, даже если оно внутри `if`/`while`. Если блок не выполнялся —
значение `NONE`.

**D12. Повторное объявление в одной функции — `REDECLARE_ERROR`.**

**D13. Объявляй до `if`.** Два объявления одного имени в `if` и `else` —
ошибка. Это цена простой модели области.

**D14. Переменная `for` — только цикл.** Она не видна после цикла, не
перекрывает внешнее имя и не может быть объявлена второй раз в той же
функции. `for i` дважды — `REDECLARE_ERROR`.

**D15. `for I 5:`** — имя капсом означает константу, цикл её присваивает →
`CONST_ERROR`. Отдельного правила не нужно.

**D16. `break`/`continue` — только в цикле, `return` — только в функции.**

## Операторы

**D17. Арифметика как в Python.** `/` — истинное деление (`7 / 2` → `3.5`);
`//` — floor (`-7 // 2` → `-4`); `%` — знак делителя (`-7 % 3` → `2`);
`**` — вправо (`2 ** 3 ** 2` → `512`); `*` — умножение.

**D18. Деление на 0 → `VALUE_ERROR`.** Отрицательная степень с дробным
показателем → `VALUE_ERROR`.

**D19. `+` со строкой → `CONCATENATE_NOT_SUPPORT` при компиляции.**

**D20. Сравнения.** `==`/`!=` — любые типы: разные типы дают `FALSE`,
`NONE == NONE` — `TRUE`. `< <= > >=` — только `flint`-`flint` и
`str`-`str` (побайтово), иначе ошибка.

**D21. Цепочки сравнений** (`0 <= x <= 10`) раскрываются в `AND`; средний
операнд вычисляется **один раз** (временная переменная).

**D22. `AND`/`OR` ленивые, результат `bool`, операнды проверяются на
истинность.** `NOT` даёт `bool`.

**D23. Истинность:** ложь только `NONE` и `FALSE`; `0`, `""`, `[]`, `{}` —
истинны.

## Строки и интерполяция

**D24. `{}` — единственная интерполяция.** `$` — обычный символ.
Работает и в строковых литералах, и в шаблонах `show`/`show_err`/`input`.

**D25. Правила `{}`:**
- `{выражение}` — подстановка; внутри обычное выражение;
- всё вне `{}` — текст: `show({x} + 1)` → `5 + 1`;
- `\{` и `\}` — литеральные скобки; `}` вне подстановки — ошибка;
- пустая подстановка `{}` — `SYNTAX_ERROR`;
- вложенные `{}` внутри выражения — литерал словаря: `show({ {a: 1} })`.

**D26. В шаблонах `show(...)` скобки `(` и `)` — синтаксис вызова**, поэтому
в тексте шаблона они экранируются: `show(a \(b\))` → `a (b)`.

**D27. Escape-последовательности:** `\\ \" \' \n \t \r \e \{ \}`. Внутри
`"..."` экранируется двойная кавычка, внутри `'...'` — одинарная; «чужая»
кавычка не экранируется.

**D28. Печать значений:** `str` на верхнем уровне без кавычек, внутри
коллекций — в кавычках; целое без `.0`, иначе до 14 значащих цифр;
`TRUE`/`FALSE`; `NONE`; `[a, b]`; `{k: v}`.

**D29. `show`/`show_err` возвращают `NONE`, `input` — `str`.**

## Коллекции

**D30. `s[i]` — строка из одного символа.** Индексы в символах UTF-8.
Отрицательный индекс — с конца. За границей → `VALUE_ERROR`.

**D31. Срезы:** правая граница не входит, открытые границы, отрицательные,
шаг. Обратный диапазон → пусто. Шаг `0` в срезе → `VALUE_ERROR`; шаг `0`
в `for` → пустой цикл.

**D32. Ключ словаря в `[]`** — только bare-имя или строковый литерал.
Переменная-ключ — через `take(k)`. Иначе `TYPE_ERROR`.

**D33. `list[T]`/`dict[K|V]`:** содержимое литерала проверяется при
компиляции; `add`/`set`/`insert` — при компиляции, если аргумент известен
статически, иначе в рантайме.

## Ошибки

**D34. `TYPE_ERROR` — компиляция, `TYPE_MISMATCH_ERROR` — рантайм.**

**D35. Ошибки с кареткой и `expected/found`.** Рантайм-ошибки тоже с
кареткой: строки исходника и карта «строка Lua → строка Kraft» вшиваются
в сгенерированный Lua. Позиция берётся по стеку и указывает на начало
выражения, в котором возникла ошибка.

**D36. Цвета только на TTY stderr.** Столбцы — в символах UTF-8.

## CLI и рантайм

**D37. Пользовательский CLI:** `./kraft file.kraft [args...]` — запуск.
`./kraft -c file.kraft` — собрать самодостаточный `.lua` рядом с исходником
(без запуска). Скрытый флаг для разработки: `--emit-lua` — печать Lua.

**D38. Сгенерированный `.lua` самодостаточен:** `krt` вшит, шебанг
`#!/usr/bin/env luajit`, строки исходника вшиты — рантайм-ошибки работают
и без исходного файла.

**D39. `args()[0]` — путь к `.kraft`-исходнику**, дальше аргументы
программы.

**D40. `NONE` в рантайме — sentinel `krt.NONE`, не `nil`.**

**D41. `dict` сохраняет порядок вставки:** `{keys = {...}, vals = {...}}`.

**D42. Манглинг имён:** переменные `v_N` по порядку объявления, функции
`f_N` по порядку объявления. Кириллица в переменных разрешена.

**D43. `continue` → `goto` (LuaJIT 2.1).** Локали поднимаются в начало
функции, переменная `for` — свой `local` внутри цикла.

**D44. `is_tty()` — FFI `isatty(2)`**, единственное LuaJIT-специфичное
место.

**D45. `time_ms()` — `os.clock() * 1000`** (процессорное время).

## Ядро и std

**D46. Ядро:** `show`, `show_err`, `input`, `type`, `str`, `flint`, `len`,
`read_file`, `write_file`, `file_exists`, `args`, `exit`, `time_ms`,
`is_tty`, `up`, `low`, `title`, методы типов.

**D47. Std на Kraft (v0.2, через импорты):** `min`, `max`, `sum`, `avg`,
`upk`, `sort`, `reverse`, `clear`, `map`, `filter`, `reduce`, `assert`,
`expect`.

**D48. `system` — v0.2**, для std и xkraft не нужен: запуск делает
обёртка `kraft`.

**D49. Импорты (`import_file`/`from_file`) — v0.2, до std.**

## Константы

**D50. Константа — имя без строчных латинских букв** (`MAX`, `MAX_SIZE`,
`X`). Присваивание → `CONST_ERROR`.

## Функции

**D51. Функция видна после объявления.** Вызов до объявления — `NAME_ERROR`.
Своё имя функция видит с начала тела: рекурсия работает. Если `->` нет,
вызывать себя нельзя — `TYPE_ERROR` («нужен явный `->`»), потому что тип
возврата ещё не выведен.

**D52. Тело функции — отдельная область.** Видны только параметры и
локальные; переменные файла — нет (`NAME_ERROR`). Функции верхнего уровня
вызывать можно. Объявления внутри тела поднимаются в начало **этой**
функции, не программы.

**D53. Возможный «провал» тела.** Если тело не заканчивается `return`,
функция может вернуть `NONE`; её результат помечается «может быть NONE», и
операции над ним проверяются в рантайме. Это же верно для `return:` и
`return NONE` при явном `->`.

## Строки: индексы, срезы, методы

**D54. `s[i]` и срезы — в символах UTF-8.** Индексация с 0, отрицательный
индекс — с конца, за границей — `VALUE_ERROR`. Срез `s[a..b]`: правая
граница не входит, границы могут быть открыты (`s[..b]`, `s[a..]`),
отрицательные индексы нормализуются, границы зажимаются в диапазон.
Шаг `0` — `VALUE_ERROR`; положительный шаг при `a > b` и отрицательный при
`a < b` дают пустую строку. `s[3..1..-1]` — обратный порядок. Шаг должен
быть целым (`VALUE_ERROR`), иначе индексы становятся дробными.

**D55. Методы строк** (0-based, индексы в символах):
`part(a, b?)` — подстрока `a..b` (без `b` — до конца);
`find(sub)` — индекс первого вхождения или `NONE`;
`contains(sub)` — `bool`;
`preff(p)` / `suff(p)` — начинается/заканчивается на `p`;
`trim()` / `triml()` / `trimr()` — убрать пробелы;
`replace(old, new)` — заменить все вхождения;
`count(sub)` — число неперекрывающихся вхождений (`""` → `0`).
`find` помечен «может быть NONE»; пустая подстрока в `replace` ничего не
меняет.

## Коллекции без параметра типа

**D56. `list` и `dict` без параметра — динамические.** Они хранят значения
любых типов. Чтение (`xs[i]`, `d[k]`, `take`) имеет внутренний тип `any`:
он совместим с любым типом при объявлении, присваивании, передаче в
функцию и `return`, а операция, которой нужен конкретный тип, проверяется
в рантайме (`TYPE_MISMATCH_ERROR`). Индекс, срез и `for-in` по `any`
выбирают тип в рантайме: `for x in v` — список, `for k, v in v` — словарь.
Метод у `any` не вызывается: сначала привяжи значение к типу
(`list row = xs[0]`), потом вызывай `row.add(...)`. `is` смотрит на
фактический тип значения. `list[flint]` / `dict[str|flint]` — после v0.1.

**D57. Литералы.** `[a, b, c]` — список, `{}` — пустой словарь,
`{ключ: значение}` — словарь. Ключ — bare-имя или строковый литерал без
интерполяции; `user[имя]` и `user["имя"]` — один ключ `"имя"`. Порядок пар
сохраняется. Повторный ключ заменяет значение и не меняет позицию.

**D58. Индексы и срезы списка** — как у строк (D54): с 0, отрицательные с
конца, за границей — `VALUE_ERROR`. Срез возвращает новый список; шаг `0` —
`VALUE_ERROR`; шаг должен быть целым (D54); пустой диапазон — пустой
список.

**D59. Чтение словаря.** `d[ключ]` и `d.take(ключ)` возвращают значение или
`NONE`, если ключа нет (не ошибка). Ключ всегда `str`; динамический ключ
(переменная, выражение) передаётся только в методы. Методы: `add(k, v)`,
`take(k)`, `remove(k)` → `bool`, `contains(k)` → `bool`,
`merge(other)` — пары `other` перезаписывают совпавшие ключи.

**D60. Методы списка.** `add(v)` — в конец; `del(i)` — по индексу
(`VALUE_ERROR` за границей); `remove(v)` → `bool`, удаляет первое
вхождение; `replace(i, v)`; `contains(v)` / `count(v)`; `index(v)` — индекс
или `NONE`; `join(sep)` — элементы через `str`, разделитель `str`.

**D61. `for ... in`.** По списку — одна переменная (элементы), по словарю —
две (ключ, значение) в порядке вставки. Коллекция вычисляется один раз.
Имена переменных подчиняются D14: `for x` дважды в одной функции —
`REDECLARE_ERROR`.

**D62. Коллекции — по ссылке.** Присваивание, передача в функцию и `for-in`
не копируют список/словарь: изменение через одну переменную видно через
другую. `==`/`!=` сравнивают ссылки (одна и та же коллекция — `TRUE`).

## Встроенные функции

**D63. Преобразования.** `len(x)` — `str` (символы UTF-8), `list`
(элементы) или `dict` (ключи). `type(x)` — имя типа текстом. `str(x)` —
печать значения как на верхнем уровне. `flint(x)`: число как есть,
`bool` → 1/0, `str` → разбор (`"abc"` → `VALUE_ERROR`), остальное —
`TYPE_MISMATCH_ERROR`.

**D64. Файлы.** `read_file(path)` возвращает весь файл как `str`; нет
файла — `FILE_ERROR`. `write_file(path, text)` перезаписывает файл целиком
и возвращает `bool`; ошибка записи — `FILE_ERROR`. `file_exists(path)` →
`bool`.

**D65. Процесс.** `args()` → `list[str]`, `[0]` — путь к исходнику (D39).
`exit(code)` завершает программу. `time_ms()` — `os.clock() * 1000`.
`is_tty()` — `isatty(2)` (D44). Имена встроенных функций зарезервированы:
объявление переменной, функции, параметра или переменной цикла с таким
именем — `NAME_ERROR`.

## Ввод для тестов

**D66. `# stdin: текст`.** Строка-комментарий с этим префиксом (отступ
разрешён) задаёт строку встроенного ввода. `input()` читает такие строки
по порядку, затем настоящий stdin. Пробелы после `:` — разделитель, пустой
хвост — пустая строка. Строки вшиваются в сгенерированный Lua, поэтому
работают и в `-c`.

## Компилятор на самом Kraft

**D67. `xkraft`.** Компилятор, написанный на замороженном v0.1 и
компилирующий сам себя. Лексер, парсер со статическими проверками и
кодогенератор живут в одном файле `xkraft.kraft`; взаимная рекурсия
запрещена, поэтому каждая рекурсивная процедура вызывает только себя.
Интерфейс совпадает с эталонным `kraft`: `--tokens`, `-c`, иначе Lua в
stdout; сам `luajit` xkraft не запускает (D48). Рантайм ищется как
`dirname(args()[0]) .. "/src/krt.lua"`. Эталонный компилятор на LuaJIT
заморожен на теге `v0.1.0` и служит проверкой: на совместимых тестах вывод
xkraft побайтово совпадает с ним. Случаи, запрещённые новыми правилами
(D77, D81), намеренно расходятся: `./kraft` остаётся компилятором v0.1.

**D68. Малое ядро, рост библиотекой.** Ядро языка v0.1 заморожено.
Новые возможности не добавляют *новых* ключевых слов и типов: слова из
«В разработке» уже зарезервированы в v0.1. Библиотечные возможности
появляются как prelude на Kraft без `import` (D80). Исключение сделано для
обработки ошибок: `try`/`trigger`/`finally` реализованы в ядре `xkraft`
(D82), потому что перехват рантайм-ошибок нельзя вынести в библиотеку.
`panic` и `froz` реализованы в D85 и D83; импорты остаются зарезервированными
и нереализованными.

## Язык после v0.1

**D69. Блочное объявление типа.** `str:`, `flint:`, `bool:`, `list:`,
`dict:` открывают блок, внутри которого каждая строка — объявление
`имя = выражение` с этим типом. Позже добавится `froz:`; модели в таких
блоках не участвуют. Действуют обычные правила имён: константы капсом,
занятые имена, повторное объявление. Блок типов — только компактная
запись, а не область видимости: имена видны до конца функции/файла, как
обычные объявления. Блоки можно писать на верхнем уровне и внутри
функций/блоков; вложенные блоки типов не нужны.

**D70. Глобальные переменные.** Верхний уровень файла — глобальная область.
Функция читает и пишет глобальные напрямую по имени: `ext` удалён из языка
и таблицы ключевых слов, слово свободно для будущих возможностей (например,
наследования моделей). Локальные объявления, параметры и переменные `for`
не могут совпадать с именами глобальных — `REDECLARE_ERROR`, поэтому запись
в глобальную из функции однозначна без маркера. Глобальная-константа
(имя капсом) читается, но запись в неё — `CONST_ERROR`. Видимость
глобальных в функциях заменяет правило «функция видит только параметры и
локальные» из D51–D53; порядок объявления, запрет взаимной рекурсии и
явный `->` для рекурсии сохраняются.

**D71. Присваивание по индексу.** `xs[i] = v`, `d[ключ] = v` (ключ — bare
имя или строковый литерал), `xs[i][j] = v`. Индекс списка — `flint`,
отрицательный отсчитывается с конца, за границей — `VALUE_ERROR`. Строка
неизменяема: `s[0] = "x"` — `TYPE_ERROR`. Для значения типа `any` проверка
в рантайме. Составные `+=` по индексу не добавляются. `list.replace(i, v)`
остаётся заменой по индексу (нужна для bootstrap `xkraft`); замена
значения — `replace_value(a, b)`.

**D72. Полный набор встроенных — ядро.** Всё из `docs/builtins.md`
доступно без библиотек: строки (`up`, `low`, `title`), числа (`abs`,
`round`, `floor`, `ceil`, `sqrt`, `min`, `max`), коллекции (`sum`, `avg`,
`keys`, `values`, `upk`, `sort`, `reverse`, `clear`), файлы, процесс
(`system`), тесты (`assert`, `expect`), функции высшего порядка (`map`,
`filter`, `reduce`). D68 уточняется: ядро включает полный набор встроенных,
stdlib — только необязательные надстройки. Ключевые решения:
`find` → `NONE`; `part` — split как в Python, подстрока — срезом;
`remove` удаляет все вхождения (с необязательным количеством); `merge`
возвращает новый словарь; `sort`/`reverse` возвращают новые списки;
`clear` меняет на месте; `round` округляет половину от нуля; `sqrt` от
отрицательного и `avg` пустого списка — `VALUE_ERROR`; `min`/`max` — от 1
до 9 аргументов или один список.

**D73. Функции как аргументы.** `map`/`filter`/`reduce` принимают функцию
по имени, без лямбд: `map(xs, double)`. Это единственное место, где имя
функции используется как значение; параметров типа `func` у пользовательских
функций пока нет. Арность `f` проверяется при компиляции: 1 для
`map`/`filter`, 2 для `reduce`.

**D74. `assert` и `expect`.** `assert(condition, message)` при ложном
условии бросает `ASSERT_ERROR` с текстом. `expect(value)` возвращает
внутренний тип `expect` с методами `equals`, `is_true`, `is_false`,
`is_none`, `contains`; провал — `EXPECT_ERROR`, успех — `NONE`.

**D75. Bootstrap `xkraft`.** Исходник `xkraft.kraft` остаётся написанным
на синтаксисе v0.1 и использует только встроенные v0.1, чтобы замороженный
эталонный компилятор мог его собрать. Новые возможности реализует `xkraft`
для компилируемых программ; сам `xkraft.kraft` их не использует. Поэтому,
в частности, `list.replace(i, v)` сохраняет смысл замены по индексу.

**D77. Верхний уровень — только объявления.** В `xkraft` новые правила
включены всегда: отдельной директивы, режима или opt-out нет. Глобальную
нельзя переприсвоить на прямой строке верхнего уровня: `x = ...` и
`x += ...` дают ошибку компиляции `TOPLEVEL_ERROR`, программа не
запускается. Глобальная — переменная, объявленная вне функции. Без
отдельной директивы сохраняется самокомпиляция: `xkraft.kraft` написан
так, чтобы не переприсваивать глобальные на верхнем уровне. Замороженный
`./kraft` по-прежнему компилирует v0.1; новая модель относится к
`./xkraft`. Новых ключевых слов вроде `mut` нет. Запись в глобальную идёт
по имени без `ext`. Имена капсом остаются жёсткими константами: запись в
них — `CONST_ERROR` в любом месте. Отдельная категория `TOPLEVEL_ERROR`
выбрана намеренно: она означает «нельзя менять здесь», тогда как
`CONST_ERROR` означает «нельзя менять никогда». Уточнение зоны изменений —
в D81. Старая строка-комментарий `# const-top` больше ничего не включает
и может быть удалена из программ.

**D78. Кеш скомпилированного `xkraft`.** Обёртка `xkraft` собирает
`xkraft.kraft` в `xkraft.lua` один раз и пересобирает только если
`xkraft.kraft` или `src/krt.lua` новее. Причина: компиляция компилятора на
каждый запуск стоила ~100 мс и перекрывала собственно время программы
(10 млн итераций цикла — ~12–20 мс, вся команда с кешем — ~30 мс).

**D79. Занятые имена — включая методы.** Все встроенные функции, ключевые
слова, типы, `TRUE/FALSE/NONE`, `Error`, а также `error` и `ANY_ERROR` и
**имена методов всех типов** (`add`, `del`, `take`, `contains`, `count`,
`join`, `part`, `trim`, `equals`, `text` и т.д.) образуют один общий список
занятых имён. Любое
объявление — переменная, параметр, функция, модель, поле или метод — с
таким именем даёт `NAME_ERROR` ещё на этапе компиляции. Раньше методы не
проверялись: `flint add = 1` и `func add(...)` компилировались, хотя `add`
уже означает метод списка и словаря. Теперь имя однозначно везде, и
стандартную библиотеку можно расширять, не опасаясь коллизий.

**D80. Std-либа без модулей.** Стандартная библиотека — prelude на самом
Kraft: `dev/prelude.kraft` компилируется в `dev/src/prelude.lua`, и компилятор
добавляет его функции к каждой программе без `import`. Пользователь вызывает
`path_join`, `now_ms`, `parse_args`, `parse_csv`, `parse_json`, `prelude_cat`
напрямую. Причины: цель — одна команда, модулей в ядре нет, а права на имена
уже зарезервированы D79. Prelude подключается по умолчанию; `--no-prelude`
убирает и объявления функций, и код из генерации. В `dist/xkraft` Lua prelude
вшит внутрь, как и рантайм.

**D81. Условие не открывает зону изменений.** Глобальную переменную можно
переприсваивать только непосредственно в теле функции или цикла (`for`,
`while`). Блоки `if`, `elif`, `else` зоной изменений не являются:
`x = ...` внутри условия даёт `TOPLEVEL_ERROR`, даже если само условие
стоит внутри функции или цикла. Причина: по месту в исходнике изменение
лежит в блоке условия, а функция или цикл находятся снаружи. Реализуется
счётчиком `cond_depth`, который увеличивается на время разбора каждой
ветки условия. Переменная, объявленная внутри условия на верхнем уровне,
также считается глобальной (D77), поэтому её переприсвоение там же тоже
запрещено; для таких изменений объявляют локальную в функции. Содержимое
обычных `list` и `dict` под это правило не подпадает: их мутируют
`add`/`del`/`remove`/`replace` везде, а `froz` неизменяем и таких изменений
не допускает.
Константы и модели не затрагиваются.

**D82. Обработка ошибок: `try` / `trigger` / `finally`.** Блок состоит ровно
из трёх частей: `try:`, одной или нескольких веток `trigger <КАТЕГОРИЯ>:` и
обязательной `finally:`. Ветка `ANY_ERROR` перехватывает всё остальное и
должна быть последней; повтор явной категории — `REDECLARE_ERROR`,
неизвестная категория — `NAME_ERROR`. В каждой ветке доступен объект
`error` модели `Error` (поля `cat`, `msg`, `file`, `line`, `col`, метод
`text()`); имя зарезервировано, запись в него — `CONST_ERROR`. Ошибка внутри
ветки `trigger` не перехватывается тем же блоком.

`finally` выполняется при любом исходе: успех, перехваченная ошибка,
неперехваченная ошибка и `return` из тела или ветки. `break`/`continue` не
могут пересекать границу `try` (`SCOPE_ERROR`), потому что телом `try` является
обёртка-замыкание. Реализация: тело и ветки выполняются через `pcall`,
успех помечается уникальной таблицей-меткой; после `finally`
неперехваченная ошибка перебрасывается через `_G.error(err, 0)`, чтобы
`krt.run` напечатал её в обычном формате с сохранённой кареткой. Зона
переприсвоения глобальных D81 от `try` не расширяется.

**D83. Типизированные коллекции и `froz`.** Параметры типа в `[]` необязательны:
`list xs` остаётся обычным списком, а `list[flint] xs`, `froz[flint] fs` и
`dict[str, flint] d` задают конкретные типы. `dict[str|flint]` равнозначно
`dict[str, flint]`: слева от разделителя тип ключа (всегда `str`), справа —
тип значения. Внутри скобок допустимы только `str`, `flint`, `bool`, один тип
или несколько через запятую. `|` работает только как разделитель пары в
`dict`; в `list`/`froz` он остаётся синтаксической ошибкой. Вложенность
(`list[list[str]]`, `froz[list[str]]`), `list[NONE]` и `dict[flint, str]`
запрещены (`TYPE_ERROR`). `froz[T]` — read-only список: чтение, индексы,
срезы и `for in` работают; запись по индексу даёт `CONST_ERROR`, мутирующие
методы — `NAME_ERROR`, срез сохраняет `froz` и спецификацию. Спецификация
проверяется при объявлении и при добавлении элементов
(`TYPE_MISMATCH_ERROR`).

**D84. Строгая ложность.** В `xkraft` `TRUE` — истина, `FALSE` и `NONE` —
ложь. Условия `if`/`while`, операнды `NOT`/`AND`/`OR` и условие `assert`
проходят проверку `check_condition`: ожидается `bool` или `NONE`. `0`, `""`,
`[]`, `{}` дают `TYPE_ERROR` на этапе компиляции. Тип `any` пропускается
статически, но проверяется в рантайме через `krt.truthy_strict`. Старый
`krt.truthy` сохранён для v0.1 и не меняется.

**D85. `panic`.** `panic("CATEGORY"[, "message"])` — оператор с category и
message в виде plain-строк. Категория должна быть из списка известных
категорий, иначе `VALUE_ERROR`; без второго аргумента сообщение равно
категории. Компилируется в `krt.fail(cat, msg)` и перехватывается обычными
`trigger CATEGORY` / `trigger ANY_ERROR`. Синтаксис `try` не расширяется:
группировка веток под общим `trigger:` отложена до этапа модулей, импортов
и пакетного менеджера.

**D86. Windows-пакет.** `dist/xkraft-win.lua` — тот же встроенный Lua-код
компилятора, что и в `dist/xkraft`, но без shell/awk-обвязки. `xkraft.cmd`
вызывает его через `luajit`, `kraft.cmd` вызывает `xkraft.cmd`.
`install-win.cmd` копирует файлы в `%LOCALAPPDATA%\Programs\kraft` или в
`%KRAFT_BIN%`, добавляет каталог в пользовательский `PATH` и проверяет
`--version`. Asset — `kraft-win.zip`. LuaJIT не входит в пакет и ставится
отдельно.

Следующие решения реализованы в `0.4.0`.

**D87. `..` — оператор диапазона.** `..` создаёт значение `range` с полями `from`, `to`, `step`. Отдельного объявления `range r = ...` нет: диапазон пишется на месте — `1..10..0.5`, `for i 1..5`, `xs[1..3]`, `if age in 0..17`. Правая граница исключена: `1..5` — это `1, 2, 3, 4`. Один разбор диапазона используется в выражениях, аргументах функций, срезах, `for` и `in`. Границы всегда целые; `1..10.0`, `1.0..10.0`, `1..10.0..0.5` дают `TYPE_ERROR`. Пустой диапазон (`5..5`) допустим; `rand_num(5..5)` (с `0.9.1` — `math.random(5..5)`, D120) даёт `VALUE_ERROR: empty range`.

**D88. Режим range задаётся формой шага.** У целого range шаг не обязателен и по умолчанию равен `1`: `1..10` и `1..10..1` — одно и то же. У дробного range шаг обязателен и должен быть записан с десятичной точкой: `1..10..1.0`, `1..10..0.5`. Границы при этом остаются целыми. Новых типов `int`/`float` не вводится: числовой тип по-прежнему один — `flint`; `range` — тип значения диапазона. `rand_num` использует шаг как сетку значений: `rand_num(1..10..0.5)` даёт `1.0, 1.5, …, 9.5`. Реализовано через `math.random` в `0.9.1` (D120).

**D89. `in` — перебор и вхождение.** `in` указывает, что переменная перебирается в коллекции или проверяется на вхождение: `for x in list1`, `for k, v in dict`, `if age in 0..17`. Для `range` проверка `in` означает попадание в полуоткрытый интервал с учётом шага. Числовой цикл по диапазону пишется без `in`: `for i 1..5:` (схематично `for i r:`); это осознанное исключение — `in` зарезервирован за перебором коллекций и проверкой вхождения, а не за синтаксисом range-цикла.

**D90. Группировка `trigger`.** `trigger CAT1, CAT2:` — один обработчик на несколько категорий; внутри доступен `error.cat` с конкретной категорией. `ANY_ERROR` пишется отдельно: объединять его с другими или повторять — `SYNTAX_ERROR`. Повтор категории в разных `trigger:` — `REDECLARE_ERROR`.

Решения, реализованные в `0.5.0`.

**D91. Экосистема — в `0.5.0`.** `kpm` и виртуальные окружения (`venv`) входят в `0.5.0`. Каноническая команда — `kpm init venv`, не `kpm venv init`. Она сразу создаёт `kraft.json`, `kraft.lock`, `venv/`, `packages/` и копию компилятора: на Linux `venv/bin/xkraft`, на Windows `venv/bin/xkraft-win.lua` и `venv/bin/xkraft.cmd`. `kpm run` — портативный способ использовать это окружение: запуск `main.kraft` через него. Реестр и модерация пакетов были намечены на `1.0.0`, но по D107 отложены на отдельный более поздний релиз.

**D92. Ключи `dict`.** Ключ — `str` или `flint`. В литерале он пишется bare-именем или кавычками: `d[имя]` ≡ `d["имя"]`. `bool`, `NONE`, коллекции и модели ключами не являются; значение может быть любым типом, включая вложенные `list`/`dict`. Динамический ключ — `d.take(k)` и `d.add(k, v)`.

**D93. Импорт без `export`.** Ключевое слово `export` удалено. Все объявления верхнего уровня модуля доступны для `import_file`, `from_file`, `import_lib` и `from_lib`; `_`-префикс не создаёт приватности. Отбор имён — ответственность импортирующего файла. Внутри `namespace` короткие имена видны в самом пространстве, снаружи доступ идёт через точку.

**D94. Минимальный stdlib.** В дистрибутив вшиты только `std/fos` и `std/cli`. `std/fos` («File Operating System») даёт `exists`, `copy`, `remove`, `read_text`, `write_text`, `read_json`, `write_json`, `read_csv`, `write_csv`; `csv_field`, `csv_line` и `csv_parse` — обычные имена верхнего уровня. `std/cli` даёт только `run(command)` и `kill(message)`. `std/fs`, `std/json`, `std/file`, `std/math`, универсальные `read`/`write`, `open`/`close`, `die` и `tty()` не добавляются. `json_parse` и `json_stringify` остаются внутренними встроенными функциями. Пункт про `std/math` пересмотрен D120.

**D95. Математика в ядре.** `fib(n)` и `factorial(n)` — встроенные функции компилятора и рантайма, не модуль stdlib. В `0.9.0` в ядро добавлена константа `PI` как ключевое слово: `show({PI})` печатает `3.1415926535898`. Пустой `std/math` не создаётся. `clamp`, `lerp` и `is_even` не вводятся вообще. Встроенный `title` остаётся, но в документации не выделяется. Запрет на `std/math` снят D120; запрет на `clamp`, `lerp` и `is_even` сохранён.

**D96. Манифест называется `deps`.** Проект описывается парой `kraft.json` + `kraft.lock`. Секция зависимостей — `deps`, не `requirements` и не `dependencies`; `requirements.txt` не используется. Зависимость задаётся локальным путём или URL и устанавливается в `packages/<name>/`.

**D97. Вывод и ввод.** Канонические функции — `show`, `show_err` и `input`. Псевдонимы `read()`, `ask()`, `echo` и `$`-синтаксис не добавляются.

**D98. Границы моделей.** До `1.0.0` не вводятся наследование, полиморфизм, инкапсуляция/приватные поля, свойства, `class` и перегрузка операторов. Модели остаются простыми: `model`, `construct`, `method`, `self`, `init`.

**D99. Строка в `flint` без явного приведения.** `flint` принимает строковое значение без вызова `flint(...)`: компилятор вставляет преобразование, если тип выражения — `str`. Правило действует в объявлениях, присваиваниях, аргументах, возвратах и начальных значениях полей моделей. Так работают `input()`, `args()`, `read_text()` и ячейки CSV. Числовой строковый литерал проверяется на компиляции (`flint n = "42"` допустимо, `flint n = "x"` — `TYPE_ERROR`); нечисловое значение извне даёт `TYPE_MISMATCH_ERROR: expected flint, found str: <значение>` при запуске. Явные `flint(x)` и `str(x)` остаются. Приведений `list()` и `dict()` нет: создание коллекции — это разбор структуры (`parse_csv`, `parse_json`, `map`), а не приведение типа.

**D100. Обновления — в `0.6.0`, выполнено.** В `0.5` компилятор не обращался к
сети и не менял установленные файлы. Логика обновления живёт в оболочке
`dist/xkraft` (`dev/update.sh`, вшивается при сборке), поэтому исходник
компилятора на Kraft и побайтовая самокомпиляция не затрагиваются. Проверка
новой версии происходит не чаще раза в сутки, только в терминале и только при
успешном запросе; таймаут 15 с, отключение через `KRAFT_NO_UPDATE_CHECK=1`.
`xkraft --update` скачивает `xkraft` и `SHA256SUMS` из GitHub Releases, сверяет
хэш и атомарно заменяет файл; на Windows обновляются файлы из `kraft-win.zip`.
Сетевые ошибки молча игнорируются при фоновой проверке и сообщаются при явном
`--update`. Обновление не перезаписывает venv проектов.

**D101. Базовый стиль — в dev, публичный линтер — в `0.8.0`, выполнено.**
`docs/style.md` остаётся источником правил. В `0.5` добавляется только
dev-скрипт `dev/tests/style.sh`: он проверяет отступы, имена, `export`,
запрещённые builtins и трейлинг-пробелы; не входит в `make check` и `dist`.
Релиз `0.7` пропущен: обе мелкие доработки объединены в `0.8.0`. Публичная
команда `xkraft lint [path...]` проверяет те же правила, работает с файлами
и каталогами на Linux и Windows и входит в `make check`. Форматтер и LSP
остаются за рамками `0.8`.

**D102. Дробный шаг range — в `0.8.0`, выполнено.** Вывод значений дробного
range стал `1.0, 1.5, 2.0, …, 9.5` вместо смеси `1, 1.5, 2`. Глобальная печать
`flint` не меняется: `fib(10)` по-прежнему даёт `55`. Выбран range-aware
подход: компилятор помечает имена Lua-переменных, пришедших из range с
дробным шагом, и для их вывода вызывает `krt.tostr_range_flint`, который
добавляет `.0` только к целым значениям. Обычные числа и integer range
не затрагиваются. Явного `fmt_flint()` нет.

**D103. LSP — после `1.0`.** В `1.0` остаются только подсветка и сниппеты для
VS Code. Компилятор получает стабильные machine-readable `--diagnostics` и
`--ast-json`, формат которых фиксируется в документации. Языковой сервер и
клиенты редакторов появляются на их базе после официального `1.0`: грамматика
фиксируется `async`-ключевым словом уже в `0.9.2` и с этого момента не меняется
до следующей разморозки (D122). Декораторы в базовую грамматику не входят.

**D104. `std/http` — в `1.1`, после async.** После официального `1.0` появляется
сетевая либа: `get(url) → str`, `post(url, body) → str`,
`download(url, path) → bool` и `get_many(urls) → list[str]`. Реализация — тонкая
обёртка над `curl` с таймаутами; на Windows — `Invoke-WebRequest`. Ошибки
получают категорию `HTTP_ERROR`. Модуль вшивается в дистрибутив, как `fos`,
`cli`, `math` и `base`. Вызовы `std/http` приостанавливаемые: внутри
`async`-функции они уступают управление event loop, вне `async` работают
синхронно; `get_many` запускает запросы параллельно на уже готовой
async-машине из `0.9.2`. D94 расширяется: публичный API становится `std/fos`,
`std/cli`, `std/math`, `std/base`, `std/http`.

**D105. Декораторы — идея без срока, не в `1.x`.** Прежний план (`deco`,
`@name`, `target()` в `1.2`) отменён D122: декораторы не входят ни в `0.9.2`,
ни в `1.0`, ни в последующие `1.x`, в `std/base` не кладутся. Идея сохраняется
лишь как набросок для следующей разморозки грамматики: `deco log():` задаёт
тело-обёртку, `target()` внутри него — маркер вызова оригинальной функции,
`@name` равнозначно `@name()`, а явный `return` меняет результат. Это было бы
чисто compile-time разворачивание, но сейчас решение не планируется к внедрению.

**D106. `async` и авто-await — в `0.9.2`.** Объявление `async name(args): ...`
занимает место `func`; `async` становится зарезервированным именем. Вызов
async-функции сразу стартует работу и возвращает future, который статически
имеет тип результата. Компилятор вставляет ожидание при первом использовании
значения (схема на тестовой приостанавливаемой операции):

```kraft
async work(flint x) -> flint:
    return timer(10, x)   # приостанавливаемая тестовая операция

flint a = work(1)   # работа уже стартовала
flint b = work(2)   # вторая тоже
show(a + b)         # здесь ждём оба результата
```

Так синтаксис «просто `async ...` и всё» даёт параллелизм без явного `await`.
В `0.9.2` приостанавливаются таймеры и тестовые future; с `1.1` к ним
добавляются вызовы `std/http` (D104). Файлы, `input()` и `system()` остаются
блокирующими. Нужны event loop в `krt.lua` и обновление грамматики VS Code.
Ошибка future поднимается в точке ожидания. С официального `1.0` грамматика
заморожена: новый синтаксис не добавляется до следующей разморозки (D122).

**D107. `0.9.0` и отложенная экосистема.** Ближайший релиз — `0.9.0`: `PI`
добавляется в ядро как встроенная константа рядом с `fib`/`factorial`;
`std/math` не создаётся, `clamp`, `lerp` и `is_even` не вводятся. В `0.9.0`
также доезжают уже лежащие в `main` исправления `kpm` (XOR и `os.execute`) и
CI. Сайт, реестр пакетов, AUR-пакет и витрина примеров, намеченные на `1.0`
(D91), откладываются на отдельный более поздний релиз; их точный номер будет
выбран отдельно. Часть D91 про реестр в `1.0.0` считается отложенной.

**D108. Граница ядро / std.** В бинарник уходит только то, что нельзя написать
на Kraft: новый синтаксис, новый тип или семантика либо то, что нужно самому
компилятору. Всё, что выражается на Kraft, живёт в std. Идея без примера кода
не становится решением. Текущие `model`, `construct`, `method`, `self` и
`init` остаются в ядре. Будущие принципы вроде наследования и полиморфизма
кладываются в std как паттерны над `model`/`dict`/`self`, а не как языковая
ООП; настоящий `class` и subtyping потребуют отдельного решения в ядре.
`async`/авто-await добавлен в ядро в `0.9.2`: это новый синтаксис и семантика,
поэтому либой он быть не может. Декораторы, `fn`-лямбды и многострочный
`show()` в ядро не входят и остаются идеями без срока (D105, D115, D123).

**D109. `..`, `show()` и `input()`.** D87/D88 уже определяют `..` как оператор
range-значения, в том числе в аргументах функций. Отдельное объявление
`range r` не требуется и не вводится: `gen_list(10..101)` и
`gen_list(1..10..0.5)` — обычные вызовы, где функция принимает range и сама
работает с `from`, `to` и `step`. Нового сахара и нового типа не нужно; отмена
D87/D88 не планируется. В `show()` и `input()` аргумент — шаблон, а не
строковый литерал: текст пишется без кавычек, а `..` внутри него — просто два
символа. Кавычку в шаблоне получают через переменную:

```kraft
str q = "\""
show({q}..{q})
```

`$`-дырки в сигнатурах (`$(flint x)`) и макросы не вводятся: задачу
`gen_list` закрывает уже существующий range из D87.

**D110. `std/base` — один модуль в `1.0`.** План «идеи без срока» отменён:
модуль вшивается в дистрибутив вместе с официальным `1.0`, как `std/math`,
без каталога подмодулей. Содержимое: `tern(cond, a, b)` — обычная функция с
жадным вычислением обеих веток; строковые helper'ы поверх `up`/`low`/`part`/
`suff`/`preff`/`find`; `render(...)` как функция над `dict`, без `$` в
грамматике; паттерны поверх `model`/`dict`/`self`, включая ООП-паттерны из
D123. Ленивый тернарный `if ... else` как выражение остаётся кандидатом в
ядро. Декораторы и многострочный `show()` в `std/base` не кладутся (D105,
D123). Отдельный модуль заводится только когда в одной теме накапливается
5+ функций. Модуль собран досрочно — он уже входит в поставку `0.9.2`, до
официального `1.0`.

**D111. `method.type` — идея без срока.** Ни в ядро, ни в std не добавляется.
Мысль: вне модели писать `method.str name(...)` или `method.flint name(...)`,
чтобы `s.name()` работало как у моделей; `self` внутри был бы значением этого
типа. Набросок ограничений: только `str` и `flint`, конфликт со встроенным или
другим пользовательским методом — `REDECLARE_ERROR`. Причина, по которой не
делаем сейчас: helper-функция с большим числом аргументов выглядит
неестественно, а сахарница ядра пока не нужна. Если идея вернётся, это будет
сахарница в бинарнике, не std.

**D112. `iinput()` — идея без срока.** Не добавляется ни в ядро, ни в std/base.
Мысль: вызов без аргументов, подсказка берётся из имени переменной:
`flint age = iinput()` → в терминале `age: `. Такое поведение потребовало бы
сахарницы ядра; пока идея остаётся на уровне мысли, как и `method.type`.

**D113. `upk` без запятых.** Планируемый вывод: разделитель — пробел, запятые
убираются: `[1, "два"]` → `1 "два"`, `{name: "Kraft"}` → `name "Kraft"`. Срок
отдельно, не в `0.9.0`; до реализации `docs/builtins.md` описывает текущий
вывод с запятыми.

**D114. `_` / `__` — соглашение, не приватность.** Префикс подсказывает
читающему, что имя или поле «внутреннее», но компилятор его не скрывает и не
ругается на обращение: `obj._x` работает. Языковой инкапсуляции нет; паттерны
с такими именами живут в std.

**D115. Лямбды: `fn`, если когда-либо.** Сейчас лямбд нет, функции передаются
по имени. Если идея вернётся, ключевое слово — `fn`, не `lambda`; срок отдельно.

**D116. Установка и обновление в `1.0`.** Оба POSIX-установщика — `install.sh`
и `install-auto.sh` — кладут в каталог команд `xkraft`, `kpm` и псевдоним
`kraft`; замороженный `kraft` v0.1 в систему не ставится. В AUR-пакете псевдоним
`kraft` не создаётся. `kpm --version` показывает `1.0.0`. Единственная команда
обновления — `kraft --update` (то же, что `xkraft --update`): она обновляет и
бинарник, и `kpm`. `kpm update` и `kpm --update` убраны; `kpm` отвечает, что
обновление делается через `kraft --update`. Логика обновления живёт только в
`dev/update.sh` и встраивается в `dist/xkraft`; дубля на Lua в `kpm.lua` нет.
Скрипт скачивает `SHA256SUMS`, `xkraft` и `kpm`, сверяет **оба** хэша до любой
замены и только после успешной проверки меняет оба файла. `kpm` обновляется,
только если он уже лежит рядом с бинарником. На Windows `kraft --update`
распаковывает `kraft-win.zip` с `xkraft-win.lua` и `kpm-win.lua`. Замена идёт
через копию во временном файле рядом с целью и `rename`: прямой `mv` из каталога
загрузки ломается на другой файловой системе. Для тестов и зеркал работают
`KRAFT_UPDATE_DOWNLOAD` (старое имя `KPM_UPDATE_DOWNLOAD` тоже принимается),
`KRAFT_UPDATE_API`, `KRAFT_NO_UPDATE_CHECK`, `KRAFT_UPDATE_CACHE`, `XKRAFT` и
`TMPDIR`. Переменной `KPM_SELF` больше нет.

**D117. `..` и `...` в срезах.** `..` — разделитель границ, `...` — разделитель
шага; это единый стиль с range в `for`, где шаг тоже отделён `..`. Соответствие
с Python: `..` ↔ `:`, `...` ↔ `::`. Формы для `xs = [10, 20, 30, 40, 50]`:

| Запись | Смысл | Результат |
| --- | --- | --- |
| `xs[..2]` | от начала до индекса 2 не включительно | `[10, 20]` |
| `xs[a..b]` | от `a` до `b` не включительно | как раньше |
| `xs[a..]` | от `a` до конца, шаг 1 | `[30, 40, 50]` |
| `xs[..]` | копия всего | `[10, 20, 30, 40, 50]` |
| `xs[a...step]` | от `a` до конца с шагом `step` | `xs[2...3]` → `[30]` |
| `xs[a...]` | то же, что `xs[a..]`, сахарница `a::` | `[30, 40, 50]` |
| `xs[...step]` | весь список с шагом `step` | `xs[...2]` → `[10, 30, 50]` |
| `xs[...]` | то же, что `xs[..]` | копия всего |
| `xs[a..b..step]` | от `a` до `b` с шагом `step` | как раньше |

Отрицательный шаг работает (`xs[4...-2]` → `[50, 30, 10]`); шаг `0` —
`VALUE_ERROR`. В циклах остаются только `for i b`, `for i a..b` и
`for i a..b..step`: у `for` нет неявной правой границы, поэтому `...`-формы
циклов не вводятся. Лексер различает `...` как отдельный op3 до разбора `..`.
Рантайм готов: `nil`-границы уже значат «от начала / до конца». Новый синтаксис
реализован в `dev/xkraft.kraft`; `dev/xkraft.kraft` не использует его в своём
теле, поэтому замороженный `kraft` v0.1 по-прежнему его собирает.

**D118. `pass` — пустой оператор.** Ключевое слово `pass` допустимо там, где
ожидается оператор, и ничего не делает. Нужно, чтобы ветка `if`/`else` или тело
цикла могло быть пустым без комментария-заглушки. В Lua оно эмитится как
`do end` — настоящий no-op, оставляющий блок непустым. Добавлено в
`dev/xkraft.kraft`, в теле компилятора не используется.

**D119. Итог аудита ядро/std перед `1.0`.** Ничего из ядра не выносится, новых
std-модулей нет. В ядре остаются `len`, `type`, `str`, `flint`; `up`, `low`,
`title`; `abs`, `round`, `floor`, `ceil`, `sqrt`, `factorial`, `fib`, `min`,
`max`; `sum`, `avg`, `keys`, `values`, `upk`, `sort`, `reverse`, `clear`;
`map`, `filter`, `reduce`; `read_file`, `write_file`, `file_exists`; `args`,
`exit`, `time_ms`, `is_tty`, `system`; `assert`, `expect`; `show`, `show_err`,
`input`; `PI`, методы строк/списков/словарей и индексы. Prelude подключается
автоматически и отключается `--no-prelude`. std — только `std/fos` и
`std/cli`; `copy_file`, `remove_file`, `json_parse`, `json_stringify`, `raise`,
`glob` — зарезервированные непубличные имена. `title` оставлен в ядре после
проверки UTF-8-семантики; раньше предлагалось вынести — предложение отозвано.
Группа чисел целиком в ядре. `keys`/`values` не выносятся: `upk` — строка для
интерполяции, а не комбинированный аксессор; перебора словаря в языке нет, для
выноса потребовался бы новый примитив. `map`/`filter`/`reduce` — ядро по D73:
пользовательские функции не могут иметь параметр типа `func`. `system`,
`assert` и `expect` — ядро по явному выбору. `PI`, `fib` и `factorial`
зафиксированы; `std/math` введён D120, `clamp`, `lerp`, `is_even` не вводятся. `upk`
остаётся строкой; идея D113 (пробел вместо запятых) без срока. `class` не
вводится: роль выполняет `model`, ООП-паттерны — в std. Лямбды, если появятся,
только `fn`; `method.type` (D111) и `iinput()` (D112) — идеи без срока.

**D120. `std/math` в `0.9.1`.** Часть D94/D95/D119, запрещавшая `std/math`,
отменена: в дистрибутив вшит третий std-модуль. Он даёт только `pow(a, b)` и
`random(x)`. `pow` — имя для уже существующего оператора `**`, новый примитив
не вводится. `random(x)` разбирает аргумент по типу: для `range` вызывается
резервированная встроенная функция `rand_num`, для списка — `rand_choice`.
Обе примитивные функции остаются непубличными: пользовательский код вызывает
их через `std/math`. Семантика `range` полностью наследует D87/D88: правая
граница исключена, шаг задаёт сетку, `random(5..5)` — `VALUE_ERROR: empty
range`. `sin`, `cos`, `tan` и `log` отложены: Lua умеет их считать, но в
компилятор вызовы не добавлены, чтобы не менять self-hosting ради четырёх
функций. `clamp`, `lerp` и `is_even` по-прежнему не вводятся — D95 в этой части
остаётся в силе. Документация по всем библиотекам собрана в `docs/libs.md`
одним файлом с частями `math`, `cli`, `fos`, затем `http` и не-std либы.
Версия `0.9.1` — бамп внутри `0.9.x`, не `1.0`.

**D121. Несколько ошибок за запуск — в `0.9.3`.** Раньше `fail()` писал только
первый `st[err]`, драйвер печатал его и выходил: файл с тремя ошибками давал
одну диагностику. Начиная с `0.9.3` компилятор собирает независимые ошибки из
разных операторов за один проход, печатает каждую через `report_error`
(категория, файл, строка, каретка) и выходит с кодом 1. Лимит — 10 ошибок,
не больше одной на строку; включать флаг не нужно, режим по умолчанию.
Каскадные `NAME_ERROR` для имён из уже упавших объявлений подавляются, а после
ошибки парсер пропускает остаток оператора или блока, включая `trigger`/`finally`.
Ошибки внутри одной строки и ошибки лексера пока остаются одиночными:
восстановление после них неоднозначно. Реализация — только в
`dev/xkraft.kraft`, замороженный `dev/kraft` v0.1 не меняется; обязательны
регрессии `multi_error_basic`, `multi_error_limit`, `multi_error_same_line`,
`self-host` и `make check`. `v0.9.1` уже опубликован, поэтому поведение
меняется отдельным релизом `0.9.3`, а не в `1.0.0`.

**D122. Путь `0.9.2` → `0.9.3` → `1.0.0` и заморозка бинарника.** `v0.9.1`
опубликован; дальше остаёмся в `0.9.x` и проверяем изменения отдельными
релизами. `0.9.2` добавил в компилятор только `async` с авто-await и event loop
(D106), без `fn`, декораторов и многострочного `show()`; `0.9.3` добавил
несколько ошибок за запуск (D121). Затем `1.0.0` — официальный релиз языка
Kraft: статическая типизация, маленький автономный self-hosted бинарник,
полноценная асинхронность и те же несколько ошибок за запуск. С `1.0.0`
бинарник и грамматика заморожены на весь `1.x`: меняются только библиотеки,
модули и фреймворки. `std/http` выходит в `1.1` как async-aware либа без правок
бинарника (D104), LSP — после `1.0` (D103). Следующая разморозка грамматики
требует отдельного решения; номера `2.0` заранее не назначается.

**D123. ООП-паттерны в `std/base` и многострочный `show()`.** В `std/base`
кладываются паттерны, а не языковое ООП: наследование — композиция с полем
родителя и явные методы-обёртки (делегирование); полиморфизм — общий протокол
из одинаковых имён методов и явный `is`-диспетчер, потому что вызов метода на
`any` запрещён; инкапсуляция — фабричные функции, `_`-имена и accessors;
дополнительно абстракция как соглашение о протоколе и примеси через
`dict.merge`. Честно фиксируются ограничения: нет `extends`, subtyping,
приватных полей, dynamic dispatch и перегрузки операторов, `is` проверяет
точный тип модели, `_` не скрывает поле (D114). Нативный многострочный
`show()` остаётся идеей без срока до следующей разморозки грамматики: в
`1.x` многострочный вывод пишется через `\n` в строках, отдельного helper'а
в `std/base` нет.

## Документация

**D76. Где что лежит.** `docs/decisions.md` — источник истины по
решениям. `docs/builtins.md` — канонический список встроенных ядра.
`docs/libs.md` — один файл с частями по всем библиотекам: `math`, `cli`, `fos`,
далее `http` и не-std либы. `README.md` — руководство и текущее поведение.
`docs/philosophy.md` — принципы языка и критерий self-hosting. `docs/rules.md`
— исторический документ, не обновляется. `docs/lua-for-kraft.md` — заметки о
Lua, не спецификация. У каждого русскоязычного документа есть английская копия
с тем же именем и суффиксом `.en.md`; RU-оригинал остаётся источником при
расхождении.
