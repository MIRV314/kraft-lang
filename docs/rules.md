# Тонкости и решения

> **Актуально на v0.1 (LuaJIT).** Источник истины — `docs/decisions.md`.
> Разделы про C-бэкенд (`kraftc`, `krt.c`, `cc`, C-слова бэкенда, эмит C)
> — история, к текущей реализации не относятся. Они сохранены как заметки
> на будущее (нативный бэкенд v1.0).

README — спека языка для программиста. Этот файл — внутренние тонкости и
решения для тех, кто пишет компилятор. Если тонкость важна читающему — она
переходит в README; сюда — только то, что нужно при реализации.

Новые решения по языку фиксируются здесь и в README **до кода**, не после.

## Формат ошибки — с кареткой, expected / found

```
TYPE_ERROR: имя_файла:12
   12 | flint x = "текст"
                        ^ expected declaration of 'x': type flint, found str
```

- первая строка: **категория: файл:номер строки**;
- затем сама строка кода с номером;
- каретка `^` точно под местом ошибки;
- пояснение — на английском, из двух частей: `expected X` (что ожидалось,
  жёлтым) и `found Y` (что найдено, красным), через запятую;
- цвета только когда stderr — терминал; иначе вывод чистый — по нему
  xkraft сравнивается с kraftc побайтово.

Тонкости реализации:

- в парсере found **формируется автоматически из текущего токена**
  (`fail`: имя, число, ключевое слово с текстом, «конец строки»…);
  задать вручную можно через `fail2` (занятое имя, рост-слово);
- в анализаторе expected — готовая строка (часто через локальный буфер),
  found — формат с именами/типами;
- столбцы считать в **символах, не в байтах** (кириллица — два байта,
  иначе каретка уедет);
- таб внутри строки: пока считать за один символ, уточнить при реализации;
- категории в v0 — только подписи при печати, обработки пока нет;
  `try` / `trigger` / `finally` / `panic` — этап роста;
- рантайм-ошибки — категория (красная на TTY) + английский текст,
  без каретки; позиции вшивать — этап роста.

Категории ошибок (полный список к справке):

`SYNTAX_ERROR`, `NAME_ERROR`, `REDECLARE_ERROR`, `CONST_ERROR`, `TYPE_ERROR`,
`SCOPE_ERROR`, `ARGCOUNT_ERROR`, `VALUE_ERROR`, `CONCATENATE_NOT_SUPPORT`,
`FILE_ERROR`, `TYPE_MISMATCH_ERROR`, `PANIC_ERROR`, `RUNTIME_ERROR`,
`GENERATE_ERROR`, `ASSERT_ERROR`, `EXPECT_ERROR`.

## Имена: что нельзя

Имя переменной, функции, параметра, метода, поля или модели не может быть:

- словом языка (`if`, `str`, `func`, `model`, `try`…);
- именем из встроенных (функции, методы типов) — см. README,
  «Зарезервированные имена»;
- **словом бэкенда**. Наш бэкенд — C, поэтому запрещены и C-слова:
  пользовательские имена идут в сгенерированный код как есть, а имена
  рантайма защищены префиксом `krt_`. Список (зафиксирован):
  типы и квалификаторы — `int`, `char`, `double`, `float`, `void`,
  `long`, `short`, `unsigned`, `signed`, `const`, `static`, `extern`,
  `struct`, `union`, `enum`, `typedef`, `sizeof`, `volatile`, `register`,
  `auto`; управляющие C — `switch`, `case`, `default`, `do`, `goto`;
  библиотека — `malloc`, `free`, `calloc`, `realloc`, `memcpy`, `memset`,
  `strlen`, `strcmp`, `printf`, `fprintf`, `sprintf`, `fopen`, `fclose`,
  `main`, `NULL`, `size_t`, `FILE`.
  (Одноимённые слова языка — `return`, `for`, `if`, `while` — отсекает
  сам лексер: это токены, не идентификаторы.)

Нарушение — `REDECLARE_ERROR` («имя занято»), как и повторное объявление
и совпадение со встроенным: ошибка при объявлении, в тексте перечисляются
занятые имена. Исключение — слова языка и `show`/`input`: это токены,
позицию имени им отдаёт уже парсер, категория `SYNTAX_ERROR`, текст тот же
(«имя занято: show — встроенная функция»).

## Анализ v0: категории

- `NAME_ERROR` — чтение необъявленного имени (видно только после
  объявления); вызов неизвестной функции; несуществующий метод у
  известного типа; имя функции не латиницей («попадает в сгенерированный
  код» — сгенерировать нельзя → `GENERATE_ERROR`);
- `REDECLARE_ERROR` — повторное объявление, «занято» (встроенные, слова
  бэкенда, конфликт функции и переменной); переменная цикла `for` —
  **тень области**: повторный `for i` законен, после цикла имя
  откатывается (к внешнему, если цикл его перекрывал); занятые слова
  (функция/встроенная/тип/C-слово) — ошибка и для цикла;
- `CONST_ERROR` — присваивание и составное присваивание имени, целиком
  набранного заглавными (`MAX`, `MAX_SIZE`);
- `TYPE_ERROR` — тип объявления/присваивания/аргумента/результата
  функции не совпал; арифметика не с числами; составные присваивания не
  с числами; срез не у строки/списка; ключ словаря в `[]` не литерал;
  `is` с неизвестным типом; `froz` и прочие «этап роста» в позиции типа;
- `CONCATENATE_NOT_SUPPORT` — `+`, если один из операндов точно строка;
- `SCOPE_ERROR` — имя файловой переменной внутри функции (в v0 `glob`
  нет — передавайте аргументом);
- `ARGCOUNT_ERROR` — арность своей функции, встроенного или метода;
- `SYNTAX_ERROR` — `break`/`continue` вне цикла, `return` вне функции
  (синтаксис допускает, генерация — нет);
- неизвестный тип выражения (вызов функции без `->`, элемент словаря) —
  проверку типа пропускаем: в языке нет вывода типов.

## self в методах

Два раздела спеки противоречили друг другу; верна подробная трактовка:

- поля создаёт **только конструктор**: `self(имя, ...)` позиционно по
  параметрам или `self.поле = значение`;
- в методе поле пишется **`self.поле`**; голое имя поля — ошибка;
- поле из метода создать нельзя — только записать в уже существующее;
- локальная переменная не может назваться как поле;
- параметр с именем поля — это параметр (поле не перекрывается);
- `return self` разрешён — ради цепочек.

```kraft
model Hero:
    construct(str name, flint hp):
        self.name = name       # поле создаётся только здесь
        self.hp = hp

    method take_damage(flint dmg):
        self.hp -= dmg         # поле — только через self
        # hp -= dmg            # ошибка: голое имя поля не видно
```

## Не в v0 (этап роста и дальше)

В базовый компилятор v0 не входят:

- **модели** (`model`, `construct`, `method`, `self`, `init`,
  статические поля) — целый раздел спеки, а для цели v0 (лексер → парсер
  → эмит C → бинарь → примеры) хватает функций и коллекций. Добавляются
  пошагово: поля → `construct` → методы → `init` → печать;
- **импорты** (`import_file`, `from_file`, `import_lib`, `from_lib`) —
  v0 работает с одним файлом;
- **`glob`** — функции в v0 полностью изолированы;
- **обработка ошибок** (`try`, `trigger`, `finally`, `panic`) — в v0
  категории ошибок существуют только как подписи при печати;
- **функции высшего порядка** (`map`, `filter`, `reduce`) — передача
  функции значением самая тяжёлая часть для парсера;
- **`froz`** — замороженные списки;
- **`assert` / `expect`** — появятся вместе с тестами (после базы);
- **внешние методы** (`method Тип.имя()`) и **именованные аргументы**
  (`init(...)` — единственное место, где они есть).

## Семантика: короткие правила

- `list`, `dict`, `froz` передаются **по ссылке**: `b = a` не копирует,
  срез копирует;
- истинность: `0`, `""`, `[]`, `{}` — **истинны**; ложь только `NONE` и
  `FALSE` (намеренно не как в Python);
- нет ключа у словаря — `NONE` и не ошибка (и индексация, и `take`);
  `remove` отсутствующего ключа → `FALSE`;
- индекс за пределами списка → `VALUE_ERROR`; шаг среза `0` →
  `VALUE_ERROR`; обратный диапазон → пустой список;
- склейки нет: `"a" + "b"` → `CONCATENATE_NOT_SUPPORT`, только
  интерполяция и `list.join`;
- числовой тип один — `flint`, он же дробный (`7 / 2` → `3.5`);
  отдельного `float` нет, `avg` возвращает `flint`;
- `sort`/`reverse` — функции, возвращают **новый** список (через
  присваивание); `add`/`del`/`remove` меняют коллекцию на месте, как и
  функция `clear(coll)` (list/dict, возвращает `NONE`);
- у dict: `add(ключ, значение)` — добавить/обновить, `remove(ключ)` —
  удалить, `take(ключ)` — по переменной-ключа; метода `set` нет;
- у строки: методов больше, чем в прежней спеке (`triml`, `trimr`,
  `count`, `remove(подстрока, количество)`), `join` у строки нет;
- переменная видна только **после** объявления (чтение выше —
  `NAME_ERROR`); невыполненный блок оставляет имя со значением `NONE`;
- параметр перекрывает поле;
- цикл `for`: диапазон без `in` (`for i 5..9:`), перебор с `in`
  (`for x in список:`); шаг `0` — пустой цикл, не ошибка;
- лимит «200 имён на файл» был лимитом прежнего бэкенда, для C
  **не вводим**;
- `is_list`/`is_dict` не нужны — проверка типа это оператор `is`;
- пустой возврат — `return:`;
- вызов функции — стейтмент: `exit(2)`, `die("х")`, `f()` (расширение
  этапа 4: без него не написать ни `exit(main())`, ни процедуры; методы
  `a.b()` уже были стейтментами);
- текст-пробел между подстановками в шаблоне сохраняется:
  `show($(x) $(y))` → `1 2` (фаза 4 поправила parse_template — раньше
  пробел между двумя подстановками схлопывался);
- **ограничение**: `\"` внутри show-шаблона работает ненадёжно (escape-
  ветка парсера съедает два токена, кавычка открывает строку). Кавычку
  в шаблоне выноси в переменную: `str q = "\""`, потом `$(q)текст$(q)`;
  в обычных строках `\"` — норм (там escape-правила лексера).

## Эмит v0: решения

Бэкенд — C11. Эмит пишет один самодостаточный файл `файл.c`: рантайм
встраивается `#include`-ом (`src/krt_all.h`, путь зашит в kraftc при сборке
— для seed-этапа это приемлемо, переносимость решится с самобинарником).
`kraftc файл.kraft` рядом кладёт бинарник `файл` (зовёт `cc`);
`--emit` — только C-файл, без cc. Ошибки cc показываются как есть.

- все значения в сгенерированном коде — `KVal` (тег + union): переменная
  любой категории может оказаться `NONE` (невыполненный блок, `flint x =
  NONE`), поэтому ни типы C, ни проверки «по статике» не спасают;
- переменные объявляются в начале своей функции (= `NONE`), присваивание —
  копия структуры; `list`/`dict` делят указатель, срез копирует;
- имена: функции — `kf_<имя>` (латиница гарантирована анализом), переменные
  — `kv_N` по порядку объявления в области: C-идентификатор не обязан
  принимать UTF-8, а исходные имена нигде не попадают в код;
- арифметика — рантаймные функции с проверками: не-число (включая `NONE`)
  → `TYPE_MISMATCH_ERROR`; деление на 0 и отрицательная степень →
  `VALUE_ERROR`; `//` — floor (Python), `%` — знак делителя;
- сравнения `==`/`!=` — любые типы: разные типы — `FALSE`, `NONE == NONE`
  — `TRUE`; `<` `<=` `>` `>=` — flint со flint, str со str (memcmp по
  байтам UTF-8), иначе `TYPE_MISMATCH_ERROR`;
- цепочки сравнений раскрываются в AND, средний операнд эмитится дважды
  (спека так и обещает); `AND`/`OR` — ленивые (C `&&`/`||` над
  истинностью), результат `bool`; `NOT` — только над `bool`;
- ординальные сравнения эмитятся как `krt_ord(a, b, "op") X 0`, где `X` —
  строго свой постфикс: `<` → `< 0`, `>` → `> 0`, `<=` → `<= 0`,
  `>=` → `>= 0` (`krt_ord` возвращает −1/0/1). Был баг: у `>` стоял
  `< 0` (как у `<`), поэтому `>` в условиях всегда давал `FALSE` при
  `a > b` и работал как `<`; пойман спайком-лексером этапа 4, починен;
- истина: не `NONE` и не `FALSE` (0, "", [], {} — истины);
- `show` собирает текст в буфер и печатает одной строкой; формат
  значений — как в разделе «Типы»: строка как значение без кавычек, но
  внутри списка/значения словаря — в кавычках; `NONE` печатается `NONE`;
  число: целое точное — без `.0`, иначе до 14 значащих цифр;
- `input`: подсказка печатается без перевода строки; сначала строки
  `# stdin:` (построчный скан исходника, отступ разрешён, пробелы после
  `:` — разделитель, пустой хвост — пустая строка), затем настоящий stdin;
  Ctrl-D → `""`;
- индексация: 0-база, отрицательный индекс — с конца, выход за границы →
  `VALUE_ERROR`; `s[i]` — по символам UTF-8; ключ словаря — строка
  (иначе `TYPE_MISMATCH_ERROR`), пропущенный ключ — `NONE`;
- срезы: открытые границы, отрицательные — с конца, шаг 0 →
  `VALUE_ERROR`, обратный диапазон → пусто; строка → строка, список →
  список; `for` со шагом `0` — пустой цикл (не ошибка, решение выше);
- `for`-диапазон: границы и шаг считаются один раз (побочные эффекты);
  шаг < 0 — сравнение через `>`, правая граница не входит;
- `for-in` — рантайм-итератор по list/dict; прочие типы →
  `TYPE_MISMATCH_ERROR`; для списка второй имени — `NONE` (два имени
  определены только у словаря);
- методы — рантайм-диспетчер `krt_method(получатель, "имя", аргументы,
  n)`: единообразно и при неизвестном статическом типе;
- встроенные — прямые `krt_len(x)`, `krt_sum(xs)` и т.д.; `min`/`max` —
  одна форма `max(список)` и две `max(a, b)`, арность 1..9;
- `time_ms()` — процессорное время; `args()` — argv собранного бинарника
  целиком (включая его имя, как «путь к исходнику» в прежней спеке).

Открытые мелочи из `builtins.md` закрыты так: `list.replace(a, b)` —
заменяет первое вхождение значения (параллельно `remove`); `upk(coll)` —
элементы в формате печати без внешних скобок, разделитель `", "`.

## Seed-версия (v0) заморожена

Перед этапом 4 (самобинарник `xkraft`) v0-подмножество заморожено: kraftc —
эталон, который `xkraft` должен воспроизвести. Что входит в заморозку:

- весь синтаксис и типы из README: `str`/`flint`/`bool`/`NONE`/list/dict,
  отступы, шаблоны `$имя`/`$(выражение)`, `show`/`input` (+ `# stdin:`);
- операторы: арифметика (`//` floor, `%` со знаком делителя, `**` вправо),
  сравнения (цепочки через AND, средний операнд дважды), `AND`/`OR`/`NOT`,
  `is`;
- циклы `while` / `for`-диапазон / `for-in` (+ break/continue), функции
  `func ... -> тип` и `return:` (пустой возврат);
- индексация (отрицательные индексы, ключ-литерал у dict через `[]`),
  срезы `a..b..шаг`, все методы строк/списков/словарей и все встроенные;
- ошибки: категории и формат с кареткой из `docs/rules.md`; рантайм-ошибки —
  `TYPE_MISMATCH_ERROR` / `VALUE_ERROR` / `FILE_ERROR` / `RUNTIME_ERROR`
  (категория + текст, без позиции).

Решения, принятые при заморозке:

- `min`/`max` — принимают **любое** число аргументов (1 — по списку, ≥2 — по
  числам); арность в анализе 1..9, рантайм не ограничивает сверху;
- `round` — как в C: половину тянет от нуля (`round(2.5)` → `3`,
  `round(-2.5)` → `-3`); спека не уточняет, взята математическая конвенция;
- bare-ключ словаря в `[]` (`user[имя]`) — литерал **только** у словаря с
  известным типом; после первого индекса тип неизвестен, поэтому
  `d2[y][z]` — внутренний ключ пишется строкой (`d2["y"]["z"]`);
- `for i` — **тень области**, не объявление: повторное `for i` в той же
  области законно (каждый цикл получает своё C-имя `kv_N`), после цикла
  имя откатывается к внешнему значению (или исчезает, если внешнего не
  было). Занятые слова (функция/встроенная/тип/C-слово) — ошибка и здесь.

Проверено на заморозке: сквозные тесты (срезы, все встроенные, края
строк/типов/NONE, пустые коллекции), рантайм-ошибки (деление на ноль,
отрицательная степень, `NONE + 1`, индекс/срез за границами, несравнимые
сравнения, `sum` строк), оба эталона из tour §18 (калькулятор, счётчик
слов); сгенерированный C чист под ASan/UBSan. Этап 3 закрыт.

## Порт лексера на Kraft (xkraft, шаг 2)

`xkraft/xkraft.kraft` — полный порт `src/lexer.c`: фреймы (TEXT/EXPR),
INDENT/DEDENT, многострочные `---`, все операторы. Паритет `--tokens`
с kraftc байт-в-байт проверен на всех фикстурах (включая формат
ошибок с кареткой). Ограничения v0, обнаруженные при порте:

- **литералы не переносятся**: строки/списки/dict — только в одну
  строку; таблицы операторов набраны плоскими списками пар
  (`["..", "DD", ...]`);
- **тела `if`/циклов — общая область видимости** (анализатор без
  вложенных областей): переменные из тел подряд идущих блоков
  конфликтуют → приходится разносить имена (`o3`/`o2`, `k3`/`k2`);
- **присваивание к элементу запрещено** («элемент меняется методом») —
  состояние лексера держится в dict, обновляется `add(ключ, значение)`;
- литерал `$` в строке — только через escape `"\$"`; символы `|`, `^`,
  `#` в шаблоне show — не токены, показываются через переменную;
- строки индексируются по символам UTF-8 — позиции (line/col) в
  символах совпадают с C-лексером без дополнительных усилий.

Производительность наивного порта: токенизация xkraft самим собой —
~2 c; оптимизация (таблицы не создавать на каждый вызов) — этап роста.

## Формат ошибок в xkraft (шаг 3)

`set_err` теперь двухчастный: `set_err(st, exp, line, col, found)` —
тексты **побайтово совпадают** с `src/lexer.c`. `report_lex` печатает
формат kraftc: категория красным, `expected X` жёлтым, `found Y`
красным — цвета только при `is_tty()` (встроенная, проверяет stderr);
при перенаправлении вывод чистый. Паритет kraftc ↔ xkraft проверен
и в пайпе, и под `script` (терминал) — байт-в-байт.

Тонкости порта:

- `found` для «неизвестный символ» и «после `$`» — **первый байт**
  символа (`c[..1]`): так же печатает C-сторона через `%c`;
- временные `fnd1`/`fnd2`/`fnd3` в `lex` — имена разнесены из-за
  общей области тел блоков (см. шаг 2);
- цвета в исходнике — escape `"\e[31m"` (новый `\e` символьный escape).

## Порт парсера на Kraft (xkraft, шаг 4)

`xkraft/xkraft.kraft` — полный порт `src/parser.c`: AST на dict/list
(узел — `{kind, line, col}` плюс опциональные поля; отсутствующий
ключ читается как `NONE` и не печатается), состояние парсера — dict
ошибок (`has_err`/`exp`/`found`/`err_line`/`err_col`, первая побеждает),
диспетчер стейтментов, `ast_dump` и `--ast`. Шаг 4а — каркас и атомы,
шаг 4б — восемь уровней выражений (`e_or`..`e_unary`), постфикс
(`index_tail`/`arglist`/`postfix_from`: индекс, срез, вызов, поле,
метода; вызов — только сразу по имени) и шаблоны (`subst`,
`parse_template`, `parse_string` для STRTEXT/DOLLAR..STREND).

Паритет `--tokens` и `--ast` с kraftc — байт-в-байт: stdout, stderr
и код возврата сверяются **отдельно по каждому потоку**; проверено
на ~50 позитивных и негативных фикстурах, на самопарсере (xkraft
парсит сам себя — md5 выводов совпадает) и в TTY (цвета под `script`).
Ошибки уходят в stderr через встроенную `show_err` (как kraftc).

Найденные при порте баги v0 и тонкости:

- **баг `parse_template` в v0 исправлен** (parser.c, коммит a4b8e64):
  литеральный `)` сразу после `$(...)` при непарной `(` в тексте
  шаблона терялся — RPAREN исключался из добора текста (`text_on` не
  включался, flush не случался). Исправление: RPAREN участвует в
  доборе текста, пустой flush безопасен (guard `b1 > b0`). 4б портирует
  уже исправленную логику;
- `trunc64` («%.64s» для found): C режет **байты**, xkraft — символы;
  расходится только на строках с многобайтовыми символами в первых
  64 байтах (в спеке-фикстурах не встречается, знаменателя паритета
  не задевает);
- литерал `$` перед закрывающей кавычкой строки (`"..."`) лексер
  читает как подстановку — в исходнике Kraft писать `"\$"`
  (decode_text вернёт `$`);
- `report_lex` в xkraft: отступ каретки нельзя резать из фиксированной
  строки — для `col > 13` позиция врала; строится циклом, как C- `%*s`;
- имена переменных внутри функции разносятся по уникальности
  (общая область тел блоков, см. шаг 2) — в порте это `i_e0`/`i_ec`,
  `t1`/`t2`, `l1`/`n1`;
- `upk`: код (`krt_upk_of`) и доки расходились на примере
  `docs/builtins.md` (старый дамп через пробел) — пример исправлен
  на разделитель `", "` (решение осталось за рантаймом).

Производительность наивного порта: xkraft парсит сам себя за ~22 c
(kraftc — 5 мс; строки конкатенируются посимвольно, каждая операция —
новая строка). Этапа роста не касается: самокомпиляция — одноразовая
сборка, ~22 с приемлемы.

## Порт эмита C (xkraft, шаг 6)

`emit_c(body, src, cpath, krtp)` — полный порт `src/emit.c`: имена
`kv_N`, отложенные объявления (`em_collect` поднимает объявления
блока наверх функции), тени переменных циклов (`em_var_shadow`),
прототипы, `main` со stdin-строками. Текст копится в список и
склеивается `join("")` в конце; запись — `write_file`. Состояние эмита
— dict, обновление — `add`/`del` (присваивание к элементу в v0
запрещено).

Тонкости, унаследованные от kraftc байт-в-байт: удвоенный отступ строки
`{` у for-циклов (`ind_` + `w` в C), двойной проход по телу функции
(collect → decls → stmts), дважды вычисляемое среднее звено цепочки
сравнений, `krt_num(1)` вместо пропущенного step.

**Паритет `.c` — функциональный** (решение шага 6). Два класса
расхождений текста, неустранимых в v0, — бинарники от них идентичны:

1. **не-ASCII и управляющие байты в строках**: kraftc пишет окталем
   (`\320\277`, `\033`), xkraft — сырыми байтами. В v0 значения байта
   не наблюдаемо: нет `ord`/`chr`, индексация и срезы строк —
   символьные, сравнения — только лексикографические (из символа
   `€` нельзя получить 226 — доказуемо);
2. **числовые литералы**: kraftc пишет `%.17g` (точное 17-значное
   представление double: `0.1` → `krt_num(0.10000000000000001)`),
   xkraft — нормализованным текстом исходного литерала (`08` → `8`,
   `.5` → `0.5`); точное раскрытие double в десятичную дробь
   требует бигнума — в v0 недоступно.

Оба класса меняют только текст `.c`: исходный текст литерала проходит
через `strtod` в тот же double. Byte-parity `.c` сохраняется для
ASCII-программ с целыми литералами и дробными, точными в двоичной
системе (`3.5`, `0.25`).

Верификация шага 6:

- `.c` kraftc ↔ xkraft: 5/8 валидных фикстур побайтово, 3 DIFF —
  только классы выше;
- поведение бинарников (stdout, stderr, rc) kraftc ↔ xkraft ↔
  самобинарник: 8/8 идентично;
- самобинарник (xkraft.c от xkraft, собран cc): `--tokens`/`--ast`
  md5 с kraftc, полный паритет 50/50, ASan/UBSan чист;
- самовыпуск детерминирован: `.c`, порождённый xkraft из
  `xkraft.kraft`, равен `.c` от самобинарника побайтово —
  фиксированная точка (gen3 = gen2); с `.c` от kraftc — только два
  задокументированных класса (см. выше), 28 строк;
- самоэмит xkraft.kraft: ~80 с (лекс+парс+анализ+эмит).

Прочее:

- путь к рантайму зашивается в `xkraft.kraft` строкой — так же, как
  `-DKFT_KRT` в kraftc через Makefile; на этапе роста может стать
  флагом;
- default-режим xkraft теперь пишет `.c` молча (строка в духе
  `xkraft: записан …` — решение шага 7);
- фикс лексера (коммит 47e1470): C принимает имя с любым байтом
  `>= 0x80`, а не только кириллицу; `DEL` (0x7F) в `is_name_start`
  проходит как старт имени — от многобайтового символа его в v0
  нельзя отличить (нет символов с первым байтом 0x80..0xC1),
  класс невалидного ввода.

## CLI-паритет (xkraft, шаг 7)

`xmain` зеркалит `src/main.c` 1:1: флаги `--tokens`/`--ast`/`--emit`
в любом порядке (до или после файла), неизвестный флаг →
`xkraft: unknown flag: X` rc 2, второй файл → `xkraft: specify only
one file` rc 2, без файла → usage rc 2, `FILE_ERROR: cannot open
file: X` rc 1. Одиночный `-` — имя файла, не флаг (как в C).
Приоритет режимов: tokens > ast > emit (как в C-цепочке if/else).

Default-режим xkraft == `--emit`: пишет `.c` и печатает
`xkraft: записан <cpath>`; у kraftc default — сборка через cc и
`kraftc: собран <binpath>` (запуск cc — забота оболочки, вариант A).
`die()` удалён — CLI-сообщения и коды возврата идут через `show_err`
и `return` (1 — файл/ошибки компиляции, 2 — CLI).

Проверка (`/tmp/opencode/p7/cli_parity.sh`): матрица 16/16 —
stdout/stderr/rc, сообщения сравниваются с заменой префикса
`kraftc` → `xkraft`; `.c` в `--emit` побайтово; формат строки
default-режима точен. Самобинарник повторяет CLI (usage, unknown
flag, emit — `.c` побайтово). Регрессии после правки: `--tokens`/
`--ast` 102/102, полный паритет 50/50, поведение бинарников 8/8,
ASan/UBSan чист; самовыпуск: gen3 = gen2 побайтово, с `.c` от kraftc —
только два задокументированных класса (28 строк).

## Самокомпиляция (xkraft, шаг 8)

Процедура (повторяемая, cc — единственная зависимость):

1. `./xkraft/xkraft xkraft/xkraft.kraft` → `xkraft/xkraft.c`
   (лекс+парс+анализ+эмит, ~80 с);
2. `cc -std=c11 -O2 -o xkraft xkraft/xkraft.c -lm` (~2 с);
3. полученный бинарник — полноценный компилятор: сам эмитит `.c`,
   запуск cc — забота оболочки (kraft-run/пользователь).

Актуализация (этап роста, шаги 1–2): процедура устарела в двух
местах — эмит идёт ~0.8 с, а не ~80 с (кеш смещений, шаг 1), и
default-режим xkraft запускает cc сам (`xkraft: собран`, шаг 2),
поэтому ручной шаг 2 остался только для потока `--emit`; реальное
время cc на самобинарник — ~9–10 с (см. «Этап роста, шаг 2»).
Доказательства ниже — снимок на момент закрытия этапа.

Доказательства (самобинарник против эталона kraftc, полный прогон
всех сьютов шагов 2–7):

- `--tokens`/`--ast` — md5 с kraftc, включая самопрогон на
  `xkraft.kraft`;
- полный паритет ошибок (stderr + rc) — 50/50;
- CLI-матрица — 16/16;
- поведение скомпилированных бинарников (stdout/stderr/rc) — 8/8;
- ASan/UBSan — чист;
- фиксированная точка: gen3 = gen2 побайтово — самобинарник
  воспроизводит свой `.c` байт-в-байт;
- `.c` от kraftc ↔ от xkraft — только два задокументированных класса
  шага 6 (28 строк), бинарники идентичны.

Этап самокомпиляции закрыт. Дальше — этап роста (оптимизация
наивного порта, отложенная библиотека для Raspberry/Arduino).

## Этап роста, шаг 1: кеш смещений строк в krt

Проблема: выпуск сам себя шёл ~80 с, время росло квадратично
(850 строк — 5 с, 1700 — 18 с, 3400 — 82 с). Профиль `-O0`:
98–99% — `krt_sym_skip`: любое обращение `src[i]` к строке
(лексер делает это на каждом символе) сканировало символы с
начала строки.

Решение — внутренняя оптимизация `src/krt_all.h`, наблюдаемое
поведение не меняется (строки неизменяемы):

- в `KStr` — кеш позиции `(c_idx, c_byte)`: «символ `c_idx`
  начинается с байта `c_byte`»; кеш двигается только на границы
  символов (инвариант);
- `krt_sym_off(i)`: вперёд — от кеша (последовательный проход
  лексера — O(1) на символ); назад — пошаговый проход влево от
  кеша по множеству границ `{0} ∪ не-байты-продолжения` (оно в
  точности совпадает с достижимым `krt_sym_skip` вперёд), так что
  взятие текста токена `src[tstart..pos]` стоит O(длины токена),
  а не O(позиции);
- `krt_bytes_to_sym` стартует от кеша; кеш двигает только если
  между позициями нет NUL (вперёд от NUL обход невозможен);
- диагностика под `KRT_DIAG` (счётчики прямых/обратных проходов)
  — без флага не собирается в код.

Точка входа одинаковая для эталона и порта — общая шапка
`krt_all.h`, поэтому верификация — дифференциальная, против
золотого снимка ДО патча:

- золото: все режимы (`--tokens`/`--ast`/полный) обоих компиляторов,
  stdout/stderr/rc отдельно, `.c`, поведение скомпилированных
  бинарников — 1783 файла; после патча `diff -r` пуст;
- паритеты: токены/AST 92/92, анализатор 50/50, CLI 16/16,
  `.c`+поведение 9/9 (FAIL=0; BYTE=4, DIFF=5 — только
  задокументированный класс окталей `\320…`/`\033`; старая запись
  «5/3 на 8» — другой состав фикстур, к патчу отношения нет);
- самокомпиляция: md5 `--tokens`/`--ast` самобинарника с kraftc
  совпадают, фиксированная точка gen3 = gen4, ASan/UBSan чист;
- тайминги: `--tokens` 82 → 0.55 с, полный выпуск 84 → 0.79 с,
  p1700 18.3 → 0.27 с; режимы теперь ограничены лексером
  (~0.55 с), парс+анализ+эмит ~0.25 с.

## Этап роста, шаг 2: автономный cc и билинг system

- default-режим xkraft теперь 1-в-1 как у kraftc: эмит + автономный
  cc + `xkraft: собран <бинарник>`; `--emit` — «только .c»
  (`записан`); провал cc → stderr `xkraft: cc exited with an error`,
  rc 1 (как kraftc);
- билинг `system(команда)` — POSIX: `/bin/sh -c` (внутренний
  `system()`); код выхода 0..255, по сигналу — 128+номер, не
  запустилось → -1; общий для kraftc и xkraft: строки в
  `analyze.c`/`emit.c` (g_globals, g_builtins, g_bi) зеркальны
  строкам `xkraft.kraft` (bl_builtins, globals-список, bl_bimap);
  в krt — `krt_system` + `<sys/wait.h>`;
- решение «default = --emit (вариант A)» из обсуждения этапа —
  переопределено: default повторяет kraftc, `--emit` остаётся
  спецрежимом «только .c»;
- сьюты усилены под автономию: полный режим сравнивает stdout
  всегда (нормализация префикса `kraftc:` → `xkraft:`), cparity
  вызывает xkraft с `--emit` (иначе его cc затирает бинарник
  kraftc — сравнение поведения пустеет), CLI — `default_msg` и
  `default_full`;
- верификация: токены/AST 36/36, полный режим 18/18, CLI 17/17,
  `.c`+поведение 10/10 (FAIL=0; BYTE=6, DIFF=4 — только
  задокументированный класс окталей `\320…`), ASan чист;
  самовыпуск `./xkraft/xkraft xkraft/xkraft.kraft` →
  `xkraft: собран xkraft/xkraft`, фиксированная точка (md5
  `.c` неизменен), md5 `--tokens` = kraftc (`7eb621fc…`);
- примечание: перезагрузка машины вымыла `/tmp/opencode` —
  тестовая инфраструктура (фикстуры/скрипты) пересоздана заново,
  состав другой, чем в записях шагов 5–8 (18 фикстур вместо
  46/50; сравнение «до/после» по записям тех шагов некорректно);
- cc-тайминги: `cc -O2` на сгенерированном C (314KB, 5036 строк)
  ~9–10 с, на исходниках kraftc (6 файлов) 1.7 с, governor
  powersave; запись шага 8 «~2 с» неточна — свойство
  сгенерированного кода (тяжёлые инлайны krt), на корректность
  не влияет; самовыпуск xkraft ~10.5 с (0.5 эмит + ~10 cc).

## Этап роста, шаг 3: рантайм отдельным объектом krt.o

Проблема: каждый `.c` включал весь рантайм (заголовок ~1250 строк
с тяжёлыми инлайнами) — cc пересобирал рантайм на каждой программе;
самовыпуск шёл ~10.5 с, из них ~10 — cc (см. шаг 2: инлайны krt —
причина, не машина).

Решение: krt разделён на интерфейс и реализацию:

- `src/krt_all.h` — только интерфейс: типы, макросы, прототипы;
  генерируемый `.c` включает его как раньше — текст `.c` не
  изменился;
- `src/krt.c` → `src/krt.o` — тела функций; собирается один раз
  (`make`) и линкуется во все компилируемые программы;
- команда cc: `cc -std=c11 -O2 -o <bin> <bin>.c <krt.o> -lm`;
  путь объекта зашивается в kraftc (`-DKFT_KRT_OBJ`, Makefile) и в
  xkraft.kraft (`krop`), kraft-run берёт `src/krt.o` рядом с собой;
- `src/krt.c` собирается с `-Wall -Wextra` — чисто.

Переходный шаг (однократно): старый xkraft эмитит новый `.c`,
линкуется вручную с krt.o — дальше самовыпуск обычный.

Доказательства: золотой снимок до/после — `diff -r` пуст по всем
режимам kraftc и xkraft (stdout/stderr/rc отдельно, `.c`, поведение
скомпилированных бинарников); паритеты: токены/AST 36/36, полный
18/18, CLI 17/17, `.c`+поведение 10/10 (BYTE=6, DIFF=4 — только класс
окталей), ASan чист; самовыпуск — фиксированная точка.

Тайминги: самовыпуск 10.5 → 7.5 с (cc 9.9 → 5.5 с); оставшиеся
~5.5 с — gcc на самом сгенерированном коде (5036 строк выражений),
рантайм сюда больше не входит; `make` (krt.o + kraftc) — 2.5 с;
линковка krt.o с программой пользователя не замедляет запуск.

## Этап роста, шаг 4: аудит паритета по всему языку

Задача: проверить, что порт покрывает весь язык kraftc, а не только
фичи, попавшие в прежние сьюиты (18 фикстур — подмножество языка).

Метод: фикстура на каждое ключевое слово/билинг/метод из README —
35 файлов (`a_` — позитивные, `e_` — негативные), прогон полного
режима (stderr/rc/stdout), токенов/AST и поведения бинарников.

Результат: **дыр нет**. Слито в основной набор (53 фикстуры):
полный паритет 53/53, токены/AST 106/106, поведение бинарников
26/26 (DIFF=9 — только класс окталей), CLI 17/17. Проверено в
частности: формы интерполяции (`$x`, `$(выражение)`, `$f(...)`,

Негативы подтвердили полный список «вне v0» (парсер kraftc, таблица

## Этап роста, шаг 5: уровень оптимизации cc (-O2 → -O1)

Задача шага — «оптимизация наивного порта» (ускорить cc на
генерируемом коде). Замеры показали, что структура эмита ни при чём,
и шаг свёлся к выбору уровня оптимизации.

Эксперименты (синтетика из вызовов `krt_*` и реальный `xkraft.c`):

- глубина вложений эмита: вложенный 9.4 с vs плоский 8.7 с — ~8%;
- разбиение гигантских функций на мелкие: 8.8 с — 0%;
- уровень оптимизации: -O0 1.5 с, **-O1 3.4 с**, -Os 6.0 с, -O2
  6.3 с, -O3 7.1 с;
- скорость бинарника: цикл из 30 млн `krt_add` — 0.110 с и на -O1,
  и на -O2: сгенерированный код — клей вызовов `krt_*`, gcc оптимизирует
  его впустую, вся работа в `krt.o` (собирается -O2, флаг пользователя
  его не трогает).

Изменение: команда cc -O2 → -O1 в трёх местах — cc-команда kraftc,
default-ветка xkraft.kraft, kraft-run; `Makefile` не тронут, там
пишется руками написанный C (krt.c, kraftc) и остаётся на -O2.
Эмитированный `.c` не меняется ни на байт (флаг в него не входит).

Результат: самовыпуск 7.5 → 4.6 с (cc ~3.4 с вместо ~5.5 с), kraftc
компилирует xkraft.kraft за ~3.1 с.

Верификация: золото пустое (все режимы + `.c` + поведение), токены
kc == xk (md5), фикс. точка (проходы 2 и 3 дают одинаковые `.c` и
бинарники), батарея без изменений (106/106, 53/53, BYTE=17 DIFF=9
beh_ok=26, CLI 17/17), ASan чист по всем 53 фикстурам, kraft-run смоук.

Вопрос «оптимизации наивного порта» закрыт окончательно: выравнивание
эмита дало бы ~0.5 с против 3 с, а синхронная правка двух эмитеров
(emit.c + xkraft.kraft) не окупается — данные зафиксированы здесь.

## Этап роста, шаг 7: run-режим обоих компиляторов

`kraftc run file.kraft [args...]` и `xkraft run file.kraft [args...]` —
компилируют и сразу запускают программу. Раньше это умел только
`kraft-run`, причём через kraftc; у самодостаточного xkraft способа
запустить файл не было.

Семантика (один в один в обоих компиляторах):

- `run` распознаётся только первым аргументом; остальные режимы не
  тронуты. Файл с именем `run` теперь недостижим напрямую (ключевое
  слово) — обходится путём вроде `./run`;
- ошибки чтения/лексера/парсера/анализа — как в default (stderr, rc 1);
  запуск без файла — usage, rc 2;
- эмит идёт во временный каталог `/tmp/kraft-run-<число>` (kraftc —
  wall-секунды `time()`, xkraft — `time_ms()`; путь нормализуется в
  сьюте), рядом с исходником ничего не появляется;
- запуск — один `system()`; аргументы кавычатся POSIX-идиомой
  (`'` → `'\''`, в C и в kraft одинаково);
- rc — билинг system: 0..255 / 128+номер сигнала / 1 (не запустился);
  в kraftc это разбор wait-статуса как в `krt_system` — libc `system`
  возвращает статус целиком (256 для rc=1 обрезался в 0, поймано
  тестом на `e_divzero`/`t_exit`);
- артефакты удаляются одинаковой командой `rm -rf ... 2>/dev/null` на
  всех путях выхода; утечек tmp нет (сьют проверяет до/после).

Новые инструменты языка, использованы: `part("/")` — basename,
`replace` с кавычиванием, пустой `join("")` — сборка команды,
`time_ms()` — имя tmp-каталога.

Верификация: `tests/run_parity.sh` — 9 кейсов байт-в-байт (вывод
программы, аргументы, rc через `exit(7)`, runtime- и compile-ошибки,
embedded stdin, usage, нет файла) + чистота каталога источника и
отсутствие tmp-течей. `make check`: 110/110, 55/55, BYTE=21 DIFF=10
NEW=0 beh_fail=0, CLI 17/17, run 9/9; фикс. точка самовыпуска
(.c и бинарники), md5 токенов kc == xk, ASan чист (55 фикстур и
run-режим), `kraft-run` не тронут и работает.

## Этап роста, шаг 9: default — запуск, компиляция — `-c`

Решение пользователя: убрать обязательное слово `run` — «просто
`./xkraft exam.kraft`» запускает программу и не оставляет мусора;
компиляция в файлы рядом с исходником (прежний default) становится
явной — флаг `-c` (как у cc). Оба компилятора меняются идентично —
паритет сохраняется.

- CLI (одинаково у kraftc и xkraft): `COMP [run] file.kraft [args...]`
  — запуск во временном каталоге, артефакты удаляются; `COMP -c
  file.kraft` — `.c` + бинарник рядом с исходником (прежний default);
  `--emit`/`--tokens`/`--ast` — без изменений. Флаги распознаются
  только первым словом: всё после файла — аргументы программы (как
  python). Usage: `COMP: usage: COMP [-c|--tokens|--ast|--emit] file.kraft [args...]`.
- Внутри: `run_mode` получил индекс файла (1 — простой вызов,
  2 — алиас `run`); dispatch по первому токену в main/xmain; `-c` —
  переменная want_compile, «хвост» компиляции не тронут. `kraft-run`
  не задет — зовёт `--emit` первым словом.
- Сьюты: an_parity/cparity — вызов с `-c`; cli_parity — `two_files`
  теперь через `-c`, плюс кейсы `usage_c_only` и `plain_missing`
  (19 кейсов); run_parity — параметр mode (run|plain) плюс 4 кейса
  простого вызова (13).
- Верификация: `make check` — 110/110, 55/55, BYTE=21 DIFF=10 NEW=0
  beh_ok=31, CLI 19/19, run 13/13; самовыпуск `./xkraft -c xkraft.kraft`
  — фикс. точка (.c и бинарник); md5 токенов kc == xk — `e408f044...`
  (сменился — в исходнике новый CLI); ASan чист (55 фикстур + run).
